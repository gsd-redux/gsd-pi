# T040 — #4289 stuck recovery under DB authority

## Context

Fix task from wave-3 review cycle 4 (`.project/review/wave-3.cycle4.md`).
`journal-integration.test.ts:381` — "#4289 runDispatch retries when
complete-milestone summary exists on disk and stuck recovery can proceed" — is
RED under `test:unit:compiled`. Attribution by 4-point file bisect: green at
`331cee83a` and at `27c224fe1` (T010), red from `942d048d7` (T029).

The fixture writes `M001-SUMMARY.md` with no DB and asserts auto mode proceeds
— the exact fallback T029 deleted when it made complete-milestone fail closed.

**This carries a judgment call. Decide it deliberately and record the reasoning.**
The precedent is R5 in `docs/dev/state-db-cutover-milestone-decision.md`, where
execute-task's filesystem consultation was retired outright because a settled DB
Attempt is the authoritative completion fact.

- **Prefer RESEED** if #4289's real subject is "stuck recovery can proceed" —
  that guarantee is still wanted, and the vehicle simply moves from a disk
  SUMMARY to a DB row. Seed the row so the recovery path is exercised.
- **INVERT only if** the test's subject is specifically "a disk SUMMARY with no
  DB row triggers recovery" — that behaviour is retired, and inverting is then
  correct. If you invert, you MUST extend R5 in the decision doc to name #4289
  and state the user-observable consequence: auto mode no longer recovers a
  stuck milestone from a SUMMARY file alone.

Do not split the difference and do not leave the test able to pass without
testing the recovery path.
