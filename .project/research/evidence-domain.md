Any external tool reading `<project>/.gsd/**` traverses the symlink into per-user home state that repo grep cannot see.
- **Source**: `src/resources/extensions/gsd/repo-identity.ts:5-6,152-160`; `src/resources/extensions/gsd/migrate-external.ts:1-40`; `docs/dev/ADR-002-external-state-directory.md:26-28`.
- **Confidence**: high
- **Why it matters here**: INTENT's constraint that "end-user state lives outside the repo" plus the external readers above means the projected-file format is a de facto public API surface; evidence of "no external readers" cannot be established from the repo alone, which bounds what `legacy:cleanup:evidence` can ever prove.

## Finding: The no-cutover gate protects 8 structural import-policy invariants plus 15 frozen behavioral witnesses — and its "required" decision imports are already DB functions

- **Claim**: `scripts/semantic-shadow-no-cutover-gate.mjs` (857 lines, AST-parsed via the TypeScript compiler API) enforces: (1) `status-response-authority` — `executeMilestoneStatus` must keep calling legacy witnesses `getMilestone`/`getSliceStatusSummary`/`getSliceTaskCounts` and must never let canonical-lifecycle bindings (`lifecycle-shadow*`, `workflow_item_lifecycles` SQL, `shadowSnapshot`) reach the public response; (2–6) decision-boundary allowlists for parallel eligibility, slice dispatch, `resolveDispatch` guards, retry ledger, and `handleAllSlicesDone` state derivation — whose *required* imports are already `gsd-db.js`/`unit-dispatches.js` functions (i.e. decisions are DB-backed; the forbidden thing is canonical *lifecycle* tables); (7) `validation-assessment-authority` — verdict resolution via `getLatestAssessmentByScope`, forbidden from promoting `"omitted"` compatibility state; (8) `closed-local-inputs` — the gate itself may not read GitHub/network/env metadata. It then runs 15 named behavioral witnesses (frozen public responses across 6 modes × 2 transports, legacy-wins-on-disagreement, DB-unavailable fail-closed, unadopted import/reconcile compatibility, park/discard DB sync).
- **Source**: `scripts/semantic-shadow-no-cutover-gate.mjs:13-128` (source inventory + witnesses), `:343-441` (status/decision boundary checks), `:491-618` (closed-local-inputs), `:646-690` (check list).
- **Confidence**: high
- **Why it matters here**: INTENT criterion 2 demands every protected invariant get an explicit post-cutover home; this finding enumerates them so retirement can be mechanical rather than interpretive — and shows most "decision" invariants need only re-pointing (they already assert DB authority), while the genuinely cutover-blocking invariants are the status-response authority boundary and the frozen-response witnesses.

## Finding: Post-cutover homes divide the gate's invariants into four classes (flip, keep, delete, port)

- **Claim**: Mapping each gate invariant to a post-cutover home: (a) FLIP — `status-response-authority` and the disagreement witnesses (`runtime-disagreement`, `resolve-dispatch-authority`, `state-derivation-authority`) become positive DB-authority checks: same AST machinery, but asserting canonical DB reads reach the response and legacy file reads do not; (b) KEEP — the DB-unavailable fail-closed witnesses (`db-unavailable-dispatch/resolver/status`) and the "never promote `omitted`" rule remain valid verbatim post-cutover; (c) DELETE-TIMEBOXED — unadopted import/reconcile and frozen-cross-mode-response witnesses live only until the ADR-046 compatibility window ("two stable releases and at least 60 days" after Import Preview/Application ship, `ADR-046.md:259-260`); (d) PORT — `closed-local-inputs` is a generic gate-hygiene check reusable on any successor gate script unchanged.
- **Source**: classification derived from `scripts/semantic-shadow-no-cutover-gate.mjs:98-128,646-676` read together with `docs/dev/ADR-046-database-authoritative-workflow-lifecycle.md:253-260` (deletion gates + compatibility window).
- **Confidence**: medium (the mapping is analysis, not an existing repo decision)
- **Why it matters here**: Gives the planner a concrete per-invariant disposition list for INTENT criterion 2, so the gate retirement PR can be reviewed as "every invariant accounted for" instead of a binary flip.

## Finding: Practitioner prior art matches the target design: single writer, derived rebuildable projections, backup-verified atomic migration

- **Claim**: Two independent practitioner sources describe the same pattern the INTENT mandates: (a) memoree's architecture doc — one daemon as single writer, "SQLite is authoritative for durable memory... FTS/vector rows are derived projections that can be rebuilt", schema migrations serialized under a lock with an "atomically publishes a verified old-schema recovery snapshot" before migrating; (b) Bugsink's single-writer SQLite write-up — WAL mode for concurrent readers, one global writer as a deliberate simplifying invariant.
- **Source**: https://memoree.dev/docs/architecture/ (opened via search result, 2026); https://www.bugsink.com/blog/database-transactions/ (2025-03-24).
- **Confidence**: medium (practitioner blogs/docs, not standards)
- **Why it matters here**: Confirms the INTENT's non-negotiables (single-writer invariant, files as rebuildable projections, verified-backup idempotent migration of `~/.gsd` state) are the accepted practitioner shape for this architecture — the milestone's design is conventional, which lowers the burden to justify it and raises the bar on migration safety details (atomic publish + verified snapshot) that prior art treats as table stakes.
